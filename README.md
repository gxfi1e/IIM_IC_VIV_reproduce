# Reproducibility Guide for 2D IIM-IBAMR Simulations

## Overview

This repository provides a representative reproducibility package for the 2D immersed interface method (IIM) simulations used in this work. It includes:

- the customized IBAMR-based solver source
- a validation-case mesh and input file
- an archived isolated-cylinder reference data
- post-processing scripts that document how case-level and campaign-level metrics were computed

Two IBAMR versions are relevant in this study:

- Validation case: IBAMR `0.14.0`
- Present production simulations: IBAMR `0.16.0`

The build workflow described below has been checked with IBAMR `0.16.0` on both a local workstation and an HPC environment.

Official IBAMR resources:

- Downloads: <https://ibamr.github.io/downloads>
- Build guide: <https://ibamr.github.io/building>
- AutoIBAMR helper project: <https://github.com/IBAMR/autoibamr>

## Folder Roles

### `example_IC_compile/`

Build directory for the customized 2D solver.

- `example.cpp`: customized 2D IBAMR/IIM solver source
- `CMakeLists.txt`: CMake build script
- `input2d`: development/test input file

### `IC_mesh/`

Mesh assets for the validation case.

- `cylinder40.e`: Exodus mesh used by the provided case

### `IC_VIV_Ur_5_data/`

Starter files for reproducing the isolated-cylinder validation case at `Ur = 5`.

- `main2d`: executable that can be used as a starting point for a rerun
- `input2d`: runtime input file for a fresh run
- `example.cpp`: source code kept with the case
- `previous_data/`: archived reference outputs from the author's run

### `IC_VIV_Ur_5_data/previous_data/`

Read-only reference force and displacement data of the archived isolated-cylinder case.

This folder contains:

- force, displacement, and coefficient histories (`CD_1.curve`, `CL_1.curve`, `CDisplacement_1.curve`, `CTD_1.curve`, `CTL_1.curve`)
- the archived timing log `simulation_log.txt`
- the processed summary `computation_results1_101_101_5.csv`
- the case-level post-processing script `post1.py`
- archived build artifacts such as `example.o` and `example.d`

### `scripts_for_post_calculation/`

Study-level post-processing scripts used to organize, derive, and visualize campaign metrics.

- `origin1.py`: scans a campaign directory for per-case `computation_results3_<SPU>_<SPD>_<UR>_<damping>.csv` files, copies them into a `post/results/` folder, and merges them into `final_results.csv`
- `post1en.py`: single-case post-processing script for the energy-harvesting workflow; reads local run outputs, computes response and power-related quantities, and writes a per-case `computation_results3_*.csv`
- `adv.py`: reads the aggregated `final_results.csv` tables for IC, CC, and CPC datasets, harmonizes column names, computes summary metrics such as peak power, peak efficiency, OAOP, OAOE, improvement factors, contribution ratios, and peak system power density, and writes `summary_IC.csv`, `summary_CC.csv`, and `summary_CPC.csv`
- `adv_plot.py`: reads the summary CSV files generated by `adv.py` and produces manuscript-level figures for OAOP, OAOE, improvement metrics, power density, and related comparative plots

## Repository Scope

This repository is organized as a reproducibility package centered on the included isolated-cylinder validation example, together with the solver source and the post-processing scripts used in the broader study workflow.

It includes:

- solver source code
- representative input files
- the validation-case mesh
- one archived isolated-cylinder reference dataset
- case-level and campaign-level post-processing scripts

Some study-level aggregation and plotting scripts are also provided for completeness, but they are designed to work with broader campaign datasets that are not bundled in this repository.

## Important Usage Note

`IC_VIV_Ur_5_data/previous_data/` is an archived data and should be kept unchanged.

For a clean separation between archived results and new results, do not run the solver inside `IC_VIV_Ur_5_data/previous_data/`, and preferably do not run directly inside `IC_VIV_Ur_5_data/` either. Create a separate working directory for your own rerun.

## Where Key Numerical Settings Are Defined

The main numerical settings are already exposed in the public repository:

- `IC_VIV_Ur_5_data/input2d` contains the case parameters, mesh path, domain size, grid spacing, refinement controls, delta-function choice, pressure/velocity jump-condition flags, CFL limit, time-step definition, boundary-condition coefficients, logging, visualization, and restart settings
- `example_IC_compile/example.cpp` shows how the customized solver is wired into IBAMR, including the use of `IIMethod`, `INSStaggeredHierarchyIntegrator`, `IBExplicitHierarchyIntegrator`, force/traction extraction, and the rigid-body coupling update
- the solver source also sets PETSc tolerances for the provided executable build path, including `-ksp_rtol = 1e-10` and `-stokes_ksp_atol = 1e-10`

For the included validation example:

- `START_TIME = 0.0`
- `END_TIME = TIMEending`
- `TIMEending = 200`
- `samping_duration = 100`

The current post-processing scripts evaluate statistical quantities over the last `samping_duration` seconds of the run.

## Build the Solver

From the repository root:

```bash
cd example_IC_compile
mkdir -p build
cd build

cmake .. \
  -DCMAKE_C_COMPILER=$(which mpicc) \
  -DCMAKE_CXX_COMPILER=$(which mpicxx) \
  -DIBAMR_DIR=/path/to/IBAMR/lib64/cmake/ibamr

cmake --build . -j
```

After a successful build, the executable `main2d` should appear in `example_IC_compile/build/`.

If your system uses environment modules, load them before configuring:

```bash
module load cmake/<cmake-version>
module load openmpi/<mpi-version>
```

## Recommended Rerun Workflow

To keep your new outputs separate from the archived reference data, create a new working directory at the repository root.

### Step 1: create a clean run folder

For example:

```bash
mkdir IC_VIV_Ur_5_run
cp IC_VIV_Ur_5_data/main2d IC_VIV_Ur_5_run/
cp IC_VIV_Ur_5_data/input2d IC_VIV_Ur_5_run/
cp IC_VIV_Ur_5_data/previous_data/post1.py IC_VIV_Ur_5_run/
```

The first two files are required. Copying `post1.py` is optional, but useful if you want to regenerate the isolated-cylinder summary for your rerun.

### Step 2: optionally replace the executable with your rebuilt one

If you compiled a new solver locally, replace the starter executable:

```bash
cp example_IC_compile/build/main2d IC_VIV_Ur_5_run/main2d
```

### Step 3: verify the mesh path

If your run directory is created exactly as shown above, the existing line in `input2d`

```text
MESH_FILENAME = "../IC_mesh/cylinder40.e"
```

can stay unchanged.

### Step 4: run the case

Serial run:

```bash
cd IC_VIV_Ur_5_run
./main2d input2d
```

Parallel MPI run:

```bash
cd IC_VIV_Ur_5_run
mpirun -np <NPROC> ./main2d input2d
```

Replace `<NPROC>` with the number of MPI processes you want to use. On some HPC systems, the executable may instead be launched through `srun` or another scheduler-integrated command.

## Post-Processing Workflow

The repository includes both case-level and study-level post-processing scripts.

### 1. Included isolated-cylinder case post-processing

`IC_VIV_Ur_5_data/previous_data/post1.py` is the archived case-level script for the included isolated-cylinder data.

It reads local run outputs from the current working directory and produces the summary CSV stored in the archive.

### 2. Per-case energy-harvesting post-processing

`scripts_for_post_calculation/post1en.py` is a single-case post-processing script for energy-harvesting runs.

At a high level, it:

- reads `input2d` and local history files
- filters the histories to the final sampling window defined by `samping_duration`
- computes response, frequency, power, efficiency, and selected added-damping or galloping-related indicators
- writes a per-case CSV named like `computation_results3_<SPU>_<SPD>_<UR>_<damping>.csv`

### 3. Per-system aggregation

`scripts_for_post_calculation/origin1.py` collects the per-case `computation_results3_*.csv` files from a study directory and merges them into `final_results.csv`.

Run this step separately for each system dataset you want to summarize, such as IC, C-C, and C-P-C.

Before reuse, edit the hard-coded `base_dir` near the top of `origin1.py` so that it points to the correct local study directory.

### 4. Study-level summary metrics

`scripts_for_post_calculation/adv.py` reads the aggregated `final_results.csv` files for the IC, C-C, and C-P-C datasets and computes the summary metrics used by the manuscript figures.

It writes:

- `summary_IC.csv`
- `summary_CC.csv`
- `summary_CPC.csv`

Before reuse, edit the hard-coded `PATH_IC`, `PATH_CC`, and `PATH_CPC` variables near the top of `adv.py` so that they point to the correct local `final_results.csv` files.

### 5. Plot generation

`scripts_for_post_calculation/adv_plot.py` reads `summary_IC.csv`, `summary_CC.csv`, and `summary_CPC.csv` and generates the comparative figures.

`adv_plot.py` assumes that the summary CSV files generated by `adv.py` are available in the working directory.

## How To Obtain the Study Metrics

To reproduce the study-level metrics from local datasets:

1. Generate case-level `computation_results3_*.csv` files using `post1en.py` for the relevant cases.
2. Run `origin1.py` for each system dataset to build its `final_results.csv`.
3. Edit `PATH_IC`, `PATH_CC`, and `PATH_CPC` in `adv.py` so they point to those `final_results.csv` files.
4. Run `adv.py` to generate `summary_IC.csv`, `summary_CC.csv`, and `summary_CPC.csv`.
5. Run `adv_plot.py` in the directory that contains the summary CSV files to generate the comparative figures.

The metric definitions themselves are implemented in `adv.py`, while `adv_plot.py` only reads the precomputed summary columns and plots them.

## Metric Definitions

The summary metrics reported by `adv.py` include peak values, OAOP, OAOE, improvement metrics, contribution ratios, and peak power density.

### OAOP and OAOE

For each `(SP_U, SP_D, damping)` group, `adv.py` sorts the available points by reduced velocity `UR` and evaluates trapezoidal averages over the simulated `UR` range:

- `OAOP = (1 / (UR_max - UR_min)) * integral P(UR) dUR`
- `OAOE = (1 / (UR_max - UR_min)) * integral eta(UR) dUR`

For the isolated-cylinder dataset, the code uses the total response as the baseline quantity:

- `OAOP_IC = OAOP_total`
- `OAOE_IC = OAOE_total`

For C-C and C-P-C datasets, UC, DC, and total values are computed separately.

### Improvement Metrics

The improvement metrics are defined relative to the isolated-cylinder baseline stored in the IC summary:

- `Delta_OAOP_UC = (OAOP_UC / OAOP_IC - 1) * 100`
- `Delta_OAOP_DC = (OAOP_DC / OAOP_IC - 1) * 100`
- `Delta_OAOP_Total = (OAOP_Total / (2 * OAOP_IC) - 1) * 100`
- `Delta_OAOE_UC = (OAOE_UC / OAOE_IC - 1) * 100`
- `Delta_OAOE_DC = (OAOE_DC / OAOE_IC - 1) * 100`
- `Delta_OAOE_Total = (OAOE_Total / OAOE_IC - 1) * 100`

Note that the total OAOP improvement is normalized by `2 * OAOP_IC`, while the total OAOE improvement is normalized by `OAOE_IC`, matching the current implementation in `adv.py`.

### OAOP and OAOE Contribution Ratios

For C-C and C-P-C cases, `adv.py` also computes the UC/DC contribution ratios:

- `pct_OAOP_UC = 100 * OAOP_UC / OAOP_Total`
- `pct_OAOP_DC = 100 * OAOP_DC / OAOP_Total`


### Power Density

In `adv.py`, power density is evaluated at each reduced velocity first, and then the reported metric is taken as the peak value within each `(SP_U, SP_D, damping)` group.

For each `UR` point:

- if the system is IC, `Y_max(UR) = Y1`, `width = D`, and `P_sys(UR) = P_total`
- if the system is C-C or C-P-C, `Y_max(UR) = max(Y1, Y2)`, `width = 2 * D + SP_U + SP_D + t`, and `P_sys(UR) = P_UC + P_DC`

The script then evaluates:

- `height(UR) = 2 * Y_max(UR) + D`
- `PD(UR) = P_sys(UR) / (width * height(UR))`

The reported summary metric is:

- `PD_peak_total = max over UR of PD(UR)`

In the current `adv.py`, the constants used in this calculation are `D = 1.0` and `t = 0.2`.

## Typical Workflow

1. Install IBAMR by following the official IBAMR build guide.
2. Build the solver in `example_IC_compile/`, or use the provided starter executable.
3. Create a clean working directory such as `IC_VIV_Ur_5_run/`.
4. Copy `main2d` and `input2d` into that new directory.
5. Run the validation case in serial or through MPI.
6. If desired, copy `post1.py` into the run directory and regenerate the isolated-cylinder summary.
7. Use the archived files in `IC_VIV_Ur_5_data/previous_data/` as the public reference snapshot.
8. For broader campaign studies, use `post1en.py` to generate per-case CSV files, `origin1.py` to merge them into `final_results.csv`, `adv.py` to compute summary metrics, and `adv_plot.py` to generate the comparative figures.

## Reproducibility Notes

- This repository includes representative input files, one archived validation snapshot, and the post-processing scripts used to define derived quantities.
- The current scripts document how metrics such as power density, OAOP, OAOE, `Delta_OAOP`, and `Delta_OAOE` were computed.
- Do not modify or overwrite files inside `IC_VIV_Ur_5_data/previous_data/` if you want to preserve the archived snapshot.
- If `input2d` is edited to use absolute paths, those paths must be updated on a new machine.
- The validation case in this package was originally run with IBAMR `0.14.0`.
- The present production simulations reported in the manuscript were run with IBAMR `0.16.0`.
- The current build procedure in this repository has been checked with IBAMR `0.16.0`.
- Exact agreement with published results requires the same source, input settings, mesh, software environment, and the corresponding full case dataset.
